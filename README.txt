WFSim 算力共享 — 便携版
=========================

怎么用
------
1. 解压或复制整个文件夹到目标电脑（Win10 x64，无需安装 Python；当前 GNU 构建
   核心也不需要安装 VC++ Redist）
2. 如果 data\config.json 不存在，首次启动会自动按当前设备生成一份默认配置并退出；
   按提示查看本 README，填写 WFSim 账号和可选的 GitHub PAT 后重新启动
3. 双击 run-portable.bat
4. 首次运行按配置的 verifier 数量启动（见 data\config.json 的 active_verifiers /
   max_verifiers）。协议 7 下每个 verifier 持有当前工作和一份 ahead 预取工作，
   两份都由心跳续期，不会因为等太久而失效；**两份都可以直接放到计算进程上并行算**，
   不再要求先交完第一份才能动第二份。

首次配置 data\config.json
--------------------
如果 data\config.json 被删除，启动客户端时会自动生成一份默认配置；它会写入当前机器的
逻辑 CPU 列表、适合本机的引擎槽位、任务宽度和一个空闲引擎起始端口，然后退出并提示
查看本 README。请填写下面几项后重新启动；其他字段没有把握就不要改，运行时缺省值会
自动补齐。

- `account.email`：WFSim 网站登录邮箱，必填。
- `account.password`：WFSim 网站登录密码，必填。`account.email` 为空时客户端会直接
  拒绝启动；密码错误时虽然能启动，但无法认领设备，积分也不会记到账号下。
- `github_pat`：可选，但建议填写。它是 GitHub fine-grained PAT，只需给公开仓库
  读取权限即可，用来提高自动检查更新时的 GitHub API 限额并显示有效期。没有 PAT
  时匿名请求也能工作，但更容易遇到 60 次/小时限制。
- `verifiers`、`claimed`：分发给新用户时建议留空 `[]` 或删除，客户端启动后会生成
  新的设备 ID；如果要在一台设备上延续原来的 verifier，可以保留。
- `known_engine`、`wire_engine`：不要手工填写，客户端会在构建和更新后写入。
- `active_verifiers`、`max_verifiers`：控制同时申请任务的验证器数量和最大数量；
  首次使用保持默认即可，之后再按机器性能调整。
- `task_logging`：四档「关 / 标准 / 详细 / 完整」，**默认 `关`**（完全不写日志，
  `logs\` 下不会新建任何文件）。平时保持默认；排查 CPU 调度或"发呆"问题时切到
  `完整`（详见下文"文件夹里有什么"一节）。

分发前请删除或清空 `logs\`、`error.log`、`data\pending-riven\` 和
`data\config.json` 中的账号密码与 `github_pat`；也可以直接删除整个 `data\config.json`，
首次启动会自动生成新设备默认配置。
任务日志可能包含账号请求、设备 ID 和任务内容，不适合作为分发包内容。

复制到另一台电脑后必须做的事
----------------------------
1. 如果两台机器同时使用同一个 verifier id，先在其中一台上点 [刷新 verifier]，
   让这台机器换一套全新的 ID。verifier id 就是"设备"，服务器只会把任务发给其中一台。
2. 如果目标电脑的 CPU 型号和打包机器不同，打开底栏 [设置]，点击
   [清理缓存重建引擎]。它会暂停接任务、清空 build-cache\target、用目标电脑的
   `target-cpu=native` 重新编译 maxperf 核心，替换成功后再恢复接任务。重建期间不要关闭
   客户端，通常需要几分钟。
   另外，引擎每次编译都会把当时的 CPU 型号写进 `engine-src\state.json`；
   复制到另一台电脑后启动时，如果型号不同，会先在控制台询问是否不用缓存重新编译。
   选 y 就按当前设备重建并安装，选 n 就直接进入主界面继续用现有引擎。
3. 如果继续使用旧电脑生成的 `data\config.json`，其中的 `engine_cores`、`work_lanes`、
   `slots` 和 `engine_base_port` 可能不适合本机。最稳妥的做法是先删除旧
   `data\config.json`，让新电脑重新生成机器默认配置，再填写账号和 PAT。

文件夹里有什么
--------------
run-portable.bat
        双击启动。
README.txt
        本文件。
src\
        客户端本体（TUI + 调度 + 状态机）。更新时整个 src\ 文件夹覆盖即可。
data\config.json
        WFSim 账号、可选的 GitHub PAT、verifier id 和各项参数。填写方法见上文。
python\
        嵌入式 Python 3.11.9 + Textual 8.2.8 及其依赖，全部纯 Python
engine\wfsim-core.exe
        Rust 计算核心（当前为 protocol 7 对应的优化 maxperf 核心）（maxperf：LTO + target-cpu=native），只跟服务器交换数据
engine\vcruntime140.dll
        当前 GNU Rust 构建的 wfsim-core.exe 不直接依赖它；保留该文件是为了兼容
        旧核心或以后切换到 MSVC 构建的情况。当前核心只依赖 Windows 系统 DLL。
error.log
        启动失败时写在这里（如果出现的话）

注意
----
- 更新客户端时，整个 `src\` 文件夹一起覆盖即可；`data\config.json`、`engine\`、`logs\` 等不要覆盖。
- `target-cpu=native` 只在编译核心的那台电脑上生效，不会因为复制文件夹而自动
  迁移到新 CPU。换到不同型号 CPU 后，建议在设置页执行一次 [清理缓存重建引擎]；
  否则旧 exe 可能只是性能较低，也可能因为缺少 native 指令而无法运行。
- 便携包内置了 GNU Rust 工具链、rust-lld 和 Cargo 依赖缓存，不需要目标电脑安装
  Rust、Visual Studio 或 MinGW。
- 每 10 分钟检查**两项**：release.json 的 engine id，以及 GitHub 上
  optimizer/src 的 tree SHA（engine id 故意不哈希 optimizer，而那就是紫卡搜索器）。
  任一变化就自动：停止取新任务 → 等已接任务算完并上传 → 归还未分配租约 →
  增量拉取 engine/webapi/optimizer/data → 应用本地优化补丁 → maxperf 编译 →
  替换 engine\wfsim-core.exe → 重新开始取任务。
  检查带 If-None-Match，源码没变时是 304，**不消耗 GitHub 限额**；出错时日志里会写明
  `local_ip=` 和 GitHub 记的 `counted_ip=`，方便分辨是谁把额度用完了。
- 更新失败不会让客户端停摆：编译失败就继续用老核心，新核心起不来会自动回滚到
  wfsim-core.prev.exe，并按 5/10/20/30 分钟退避重试。
- 编译中间产物保存在 build-cache\target，Cargo 缓存在 toolchain\cargo。
  同步只重写内容变化的文件，没变的文件保持原 mtime，Cargo 会走增量编译。
- `task_logging` 控制 `logs\` 下的调试日志：日志会对 `password`、`cookie`、
  `authorization`、`github_pat`、`token`、`secret`、`api_key` 等字段脱敏，
  不会把明文账号信息或 PAT 写进日志。
  设置页「日志详细级别」四档，对应 `data\config.json` 的 `task_logging`：
  **关**（`off`，**默认**）整份不写，连 `logs\` 目录都不会创建，几乎没有开销；
  **标准**（`standard`）只记错误和会话起止；**详细**（`verbose`）在标准之外
  追加会话/计时/申请与上传的常规记录，但省略折叠累加器等大对象（只留省略标记）；
  **完整**（`full`）保留全部正文，并额外记录 CPU 调度明细（每个计算进程实际生效的
  亲和掩码与 CPU 集合、每行计算实际消耗的 CPU 秒数与等效核心数、每个进程的空闲时段
  及原因），用于排查"算完一个任务后发呆"。设置页可以随时切档，切到 `关` 立即停写、
  再从 `关` 切回来会新建当次运行的文件。旧配置里的 `summary` 按「详细」读取，
  更早的 `true`/`false` 分别按「详细」/「关」之外的语义读作「标准」/「关」。
  `events-YYYYmmdd-HHMMSS.jsonl` 记录申请、计算调用、上传请求/响应和错误，
  **每次启动新建一个文件**（重启不会追加到上一次运行的文件里）；
  `logs\tasks\<lease>.jsonl` 按 lease 追加保存任务输入、结果摘要和服务器返回。
- **紫卡答案先落盘再上传**：算完的紫卡答案会先写进 `data\pending-riven\<lease>.json`，
  上传成功后立即删除。发送失败（断网、进程崩溃、重启）时答案不会丢：客户端仍持有该租约
  并继续续约，每 15 秒自动重发一次，直到服务器确认收到为止。服务器说"这不是你的租约了"
  或超过 10 分钟仍未收下，才放弃并写一条 `riven_pending_*` 日志。
  暂停（p）和退出（q）都会**先尝试把待发的答案送出去**：暂停时如果还没送成功，这条紫卡不会
  归还租约（归还了服务器就不再收这条答案），而是把验证器腾出来、让答案留在盘上继续补发。
  这个目录只是运行状态，分发前请清空。
- 第一次构建或 engine 源码真正变化时需要几分钟；只改 webapi 等小范围文件时
  通常只重编少数 crate。按 u 可手动检查更新；设置页的 [清理缓存重建引擎] 会强制
  使用 `--clean` 从空缓存重建，专门用于换机后的 CPU native 优化。
- 任务状态按上游接口查询：每个 verifier 每 30 秒最多各查一次榜单和紫卡，榜单使用
  `/api/board/mine`，紫卡使用 `/api/appraise/mine`，每次最多 60 条尚未最终确认的
  任务。`confirmed` 和 `gone` 是最终状态，不再重复查询。顶部“无效”和每个 verifier
  的“无效”都来自同一份任务状态账本；`gone` 只表示服务器已不再计分，不等同于判定
  客户端一定算错。
- 更新源是 GitHub 的 main 分支，不依赖 release.json 里那个可能没有推送到 GitHub
  的生成 commit；服务器返回的 engine id 作为最终兼容版本写入配置。
- build-cache 跟随文件夹一起复制；Cargo 的增量缓存对路径敏感，保持文件夹路径
  不变时会直接复用，换到不同路径后第一次构建可能需要重编。
- 超过 64 个逻辑处理器或多 processor group 的服务器：当前代码用 CPU Sets 记录全部
  逻辑处理器，`max` 模式会把整物理核心按 P/E 均衡分给各进程；但 Windows 的进程
  亲和掩码是分组作用域的，完整的跨 group 绑定还没有实现，单线程任务的“钉核”也
  只在第一个 group 内生效。`work_lanes` 会被上限 256 截断（服务器只接受 ≤256 的
  lane 声明），本机实际计算线程数不受这个上限影响。
- CPU 核心页（底部 [CPU 核心 / 限速] 按钮）可以做两件事：
  1. **核心类型**四选一（交给 Windows / 优先 P 核 / 最高效率优先 / 优先 E 核）。
     它用 Windows 的 CPU Sets 把计算线程安排到对应那一类核上，并同时开关 EcoQoS。
     - 优先 P 核 / 优先 E 核：只在 Intel 大小核上生效。
     - 最高效率优先：把整物理核心按 P/E 均衡分给每个计算进程。先平分 P 核，
       再用 E 核补齐线程数最少的进程，所以各进程的总线程数接近相等，并且每个
       进程至少拿到一个 P 核（例如 8P+16E、3 进程 -> 3P+5E / 3P+5E / 2P+6E，
       合计 8/8/8）。每个槽的 CPU Sets 都按“性能核在前”排序，单线程任务会优先
       落在本进程性能最高的核心上；整槽线程数为 1 时还会临时把进程钉在这个最高
       核心上，跑完自动恢复。
     - 该模式按“逻辑线程”绑定，并按“整物理核心”分配：支持超线程的机器会
       用满每个核心的线程，同核线程不会跨进程拆分；页面会显示超线程开/关、
       每槽 P/E 数和每槽“核心 / 线程”数。
     - 分配失败会自动回落，不需要用户干预：均衡计划先自检（每槽非空、每槽至少
       一个最高性能核、线程数偏差不超过一个核心、CPU 记录无重复/未知项）；不通过
       就先回落到按 LLC/类别分组，再不行就把所有逻辑处理器完全平均分给各进程，
       最后连 CPU 记录都读不到就交给 Windows 自行调度。
     **只影响调度，不影响计算结果。**
  2. **手动勾选核心**，把引擎进程限制在指定的逻辑处理器上（任务管理器的 CPU 0 … 23）。
     不勾任何核心 = 恢复全部核心。
- **设置页的界面缩放**：50% / 75% / 100% / 125% / 150% / 175% / 200%，以及“跟随系统”。
  Textual 自己不能缩放文字，所以这一项改的是当前 Windows Terminal 配置档的
  `font.size`：100% 是不按 Windows 全局缩放放大的字号，150% 对应 Windows 150% 的
  当前观感。写回前会留一份 `settings.json.wfsim-backup`，选“跟随系统”恢复原字号；
  不是 Windows Terminal（经典控制台）时该项不生效，但选择会保存在配置里。
- 同一页顶部有 CPU CAP，10% 到 100%，每 10% 一档。它用 Windows
  的硬性 CPU 限流控制三个引擎进程，改档立即生效；玩游戏时可以先调到
  30% 或 50%。


租约、暂停与退出
----------------
- **租约是心跳，不是死线**。榜单包会按行续约（距到期不足 2 分钟就续，每次续 5 分钟），
  紫卡每 2 分钟续一次；只要还在算，就不会被收走。服务端说 held=false（别人拿走了）
  才放弃那一行。
- **队列（ahead）任务只在 `queue_fallback=1`（强制队列）时续约**：关闭强制队列时，
  当前任务照常续约，但队列里的那一份不再续约，会按它自己的租约自然过期并由服务器
  收回。这是刻意的：不强制队列时，客户端不再替一份不急着算的工作占住行。
- **强制队列（`queue_fallback=1`）下，答案必须"手里已经有下一包"才交**：交出去就等于
  空手，而服务器只会把"有人在等的题目"（紫卡）发给空手的客户端 —— 强制队列又要立刻
  退掉它并付 70 秒冷却。所以没有队列时，答案会**一直压着**（`results` 里点名，租约照常
  续），同时按服务端给的节奏（`next_ms`）反复申请下一包，直到拿到为止。中间批次也拦。
  三个例外（优先级从高到低）：暂停/维护/引擎更新/退出；正在交还的包；**已宣告退役的备胎**
  且常驻 ver 已全部接到 board。
- `board_submit_hold_ms`：上面那条"压着不交"的时间上限，**毫秒**，默认 `3600000`（1 小时）。
  到时不管有没有队列都会提交 —— 因为服务端自己的 `row_ceiling_ms` 是 2 小时，过了那个点
  别的客户端也可以接同一行，再压只会把已经算好的活让给别人。实际生效值是
  `min(本项, 服务端下发的 row_ceiling_ms)`；填 `0` 或删掉则用内置的 1 小时。
- **暂停（p）**：立刻停止申请新任务，把**还没开始算的**工作还给服务器；
  **正在算的行不打断**，算完上传后那一包剩余的行也一起退回。算完空闲的引擎会关闭，
  它的线程**并给还在算的引擎**，让最后几行尽快收尾。再按一次 p 恢复成三个引擎各用各的。
- **退出（q）**：先向服务器归还当前持有的全部任务（正在算的紫卡会先取消优化器），
  最多等 30 秒，然后才关闭。Ctrl+C 走同一条路。
- **待处理紫卡上限**（底栏 `待处理紫卡 －/＋`，配置项 `riven_pending_max`）：
  待分配池里最多留几张紫卡，超过就不再申请。**正在计算的不算在内。**
- 任务优先级：**先做榜单**。调度器把每个 verifier 的两份工作（当前的和 ahead 预取的）
  一起放进候选池，榜单行永远排在紫卡前面；某一份榜单算完上传后立刻再申请一份 ahead，
  期间空闲进程会去所有 verifier 的候选池里找榜单，只有本地确实没有任何待算榜单行时
  才去算紫卡（单行和 20 行包一视同仁）。手动点选的优先任务仍然高于榜单优先。
- **超时保护**（配置项 `stale_start_promote_seconds`，默认 2400 秒 = 40 分钟）：
  任务领取到手后 40 分钟还没被任何计算进程开始，就在下一次挑任务时临时排到第一，
  优先级**与手动点选同级**；同级之间仍按“榜单优先、租约最先到期优先”判定，所以
  其中一个被拿去计算后，这一级只剩另一个，下一次必然被拿走。配置里写 0 关闭该机制，
  删除这一项则沿用 40 分钟默认值。
- **引擎拒绝单行不影响整包**：如果某一行本身无法计算（例如近战榜单行没有架势，
  引擎在 `/api/board/order` 直接拒绝），只跳过这一行，同包其余行照常计算并上传；
  这一行随 `done=true` 交还服务器（服务器**不会**把它标记为异常，将来可能再次派发）。
  它不计入“本地无效”，日志里记为 `row_refused`，界面提示“引擎拒绝这一行，已跳过”。
